# Web App Architect — Decision Heuristics (H Detail)

> 外置自 `skills-source/web-app-architect/SKILL.md` §H。
> 主 SKILL.md 只保留标题，详细展开在本文件。

---

## H1. 何时优先 modular monolith

优先 modular monolith，当：

- 只有一个主要 Web 客户端
- 团队很小
- 业务边界还在变化
- 部署与排障成本要尽量低
- 数据模型之间高度相关
- 多数页面共享组件和交互模式

---

## H2. 何时才考虑拆服务

只有在以下条件明确成立时才建议：

- 某能力有显著独立扩缩容需求
- 某能力有独立发布节奏
- 某能力有明确的数据或权限边界
- 某能力已成为主应用的复杂度瓶颈
- 拆出来后整体复杂度净下降，而非上升

---

## H3. 何时考虑独立 BFF

考虑独立 BFF，当：

- 前端不止一个客户端类型
- 同一后端 API 已被不同前端不断"定制化污染"
- 需要为某一前端做专门的数据聚合与权限裁剪

否则默认不做。

---

## H4. 何时优先服务端/路由级获取

优先服务端/路由级获取，当：

- 首屏必须立即看到数据
- 数据可由服务端安全获得
- 页面是重数据页
- 可以并行预取多个关键请求
- 需要减少客户端 waterfall

---

## H5. 何时允许客户端获取

客户端获取更合适，当：

- 查询明显由用户交互触发
- 数据依赖浏览器环境
- 局部刷新比整页刷新更合理
- 需要长驻前端缓存与后台重取

---

## H6. 何时使用共享状态管理

只有当至少满足其一时才引入共享状态方案：

- 多层级组件传值已明显影响可维护性
- 多个页面需要共享同一轻量会话态
- 某个复杂 screen 需要 reducer 风格的集中状态变更

不要因为"项目都会有 store"就引入全局 store。

---

## H7. 何时引入后台任务 / 队列 / worker

考虑后台任务或异步 worker，当：

- 文件导入解析较慢
- AI 推理、批处理、通知发送不适合同步阻塞请求
- 某些任务需要重试 / 补偿 / 进度追踪

否则先保持同步链路简单。
