## 必须主动报警的反模式

### 反模式 1：把页面结构当数据结构
把"驾驶舱表""主页数据表""详情页表"当成数据模型名。页面会变，数据结构应相对稳定。

### 反模式 2：把 AI 输出直接写进正式层
没有 review、没有版本、没有来源追溯。AI 结果默认先进入 raw / extracted / review，不直接进入 canonical。

### 反模式 3：所有扩展都塞 JSON
短期快，长期几乎必乱。关键业务字段不应长期埋在 JSON 里。JSON 只用于：原始导入 payload、外部半结构化数据、未稳定扩展字段、调试快照。

### 反模式 4：列表接口各写各的查询规则
不同列表用不同分页参数名（`pageNo` / `current` / `offset`）、不同筛选格式、不同排序语法。维护痛苦。

### 反模式 5：状态自由跳转
没有状态机与前置条件。用户可以从任意状态跳到任意状态，导致数据不一致和审核漏洞。

### 反模式 6：更新接口自由覆盖整个对象
直接把整个对象 PUT/PATCH，容易误改系统字段、审计字段和只读字段。应使用白名单式字段更新。

### 反模式 7：schema breaking change 一步到位
直接改字段名、改类型、删除旧字段、改 API 结构，没有兼容期、没有 backfill、没有验证。

### 反模式 8：没有 source-of-truth 说明
设计文档不说明哪个字段才是正式值，最后没人知道哪个算 canonical。

### 反模式 9：聚合 view model 反客为主
为了页面方便把聚合结果当成底层真相对象，导致写入和追溯混乱。聚合查询服务于读取，不承担核心写入真相。

### 反模式 10：把认证当成授权
只校验"是否登录"，却不校验"是否有资格编辑 / approve / publish"。即使企业登录已存在，仍需明确产品内权限边界。
