# WebApp Interaction Designer — Detailed Checks

> 外置自 `SKILL.md` §Step 0–9 / §诊断模式 / §AI 交互类型识别。
> 主 SKILL.md 只保留步骤标题与核心意图，详细展开在本文件。

---

## Step 0: 三层目标识别（必须执行）

设计前先明确：

| 层次 | 说明 |
|------|------|
| 业务目标 | 产品/组织要达成的结果 |
| 用户目标 | 用户要完成的任务与期望体验 |
| 系统约束 | 权限、合规、审计、性能、数据前提、同步方式 |

必须写清：
- 三者是否一致
- 必要摩擦在哪里
- 冲突时优先保护什么
- 哪些步骤因为合规/风控/审计不能被"优化掉"

---

## Step 1: 识别产品与任务场景

至少输出：
- 产品类型
- 用户角色
- 高频任务
- 低频高风险任务
- 当前页面在流程中的位置
- 涉及能力（审批 / 批量 / AI / 上传 / 下载 / 协作 / 权限）
- 使用场景（桌面 / 移动 / 多人）
- 关键 persona
- 与数据前提相关的限制（如需 sync / state / backfill）

---

## Step 2: 拆解用户任务流

针对核心任务，明确：
- 用户目标
- 触发点
- 关键步骤
- 决策点
- 系统反馈点
- 风险点
- 中断点
- 回退点
- 完成态 / 取消态 / 失败态

还必须指出：
- 哪一步最容易出错
- 哪一步最需要确认
- 哪一步最需要减少摩擦
- 哪一步必须可撤销或可恢复

---

## Step 3: 定义交互策略

至少覆盖：
- 导航策略
- 列表 / 详情关系
- 搜索 / 筛选 / 排序 / 批量操作
- 表单交互策略
- 自动保存 / 草稿策略
- 多步骤流程策略
- 危险操作策略
- 协作 / 审批策略
- AI 功能策略
- 数据未就绪时的 fallback 策略

新增要求：对每条策略，尽量补一句：
- 为什么这样设计
- 如果不这样会出现什么风险

---

## Step 4: 建立状态系统

必须覆盖至少这些状态：
- default / hover / active / focus / selected / disabled / read-only
- loading / empty / success / warning / error / partial success
- timeout / retry / permission denied / conflict / version mismatch
- destructive confirm / undo available / sync pending / not ready

每种状态都要写明：
- 用户能否继续操作
- 系统显示什么
- 用户下一步能做什么
- 是否保留上下文
- 若是数据前提问题，用户是否需要知道"数据未准备好"

---

## Step 5: 等待与反馈机制

按等待类型区分：
- 即时反馈 / 短等待 / 中等待 / 长等待 / 后台任务 / 异步完成通知

必须明确：
- 用户是否知道系统已收到请求
- 等待时是否能继续其他操作
- 长任务是否可取消
- 完成后在哪里通知
- 是 toast、inline、progress、skeleton 还是持久通知

新增要求：对于 AI 与后台任务，要区分：
- 已提交 / 处理中 / 部分完成 / 需要人工确认 / 已执行 / 仅建议

---

## Step 6: 异常与恢复设计

必须覆盖：
- 错误类型分类
- 用户能理解的错误文案
- 可恢复 vs 不可恢复
- retry 机制 / fallback 机制 / draft 保留
- undo / revert / 冲突解决
- 权限不足 / 数据未同步 / 状态未初始化 / 字段缺值时的表现
- AI 结果不可靠时的修正路径

新增要求：显式区分 5 类问题，不能混为普通 `error`：
1. 代码错误
2. 用户输入错误
3. 权限问题
4. 数据前提未完成
5. AI 不确定性问题

---

## Step 7: 无障碍与操作效率

必须写清：
- tab 顺序 / focus 管理 / target size
- form label / hint / error 关联
- dialog / drawer 的焦点与关闭逻辑
- 快捷键 / 快捷入口（若适用）
- 不只靠颜色表达状态

---

## Step 8: 交付物输出

最终输出必须拆成实际交付物：

### A. 给 PM / 业务方
核心任务流、关键决策点、风险点、必要摩擦、修补 vs 重构建议

### B. 给前端
页面行为说明、组件交互说明、状态矩阵、异常与恢复逻辑、焦点/键盘/a11y 注意事项、页面间跳转与返回行为

### C. 给后端 / 数据层
页面依赖字段清单、状态对象要求、权限与错误模型需求、哪些 fallback 实际是"数据未准备好"、是否依赖 sync / init-state / backfill / seed

### D. 给测试 / 上线前审查
必测主路径、必测 persona、必测状态、必测异常与恢复、哪些问题属于 blocker

### E. 给 frontend-design
页面骨架、需视觉强调的交互元素、状态清单、关键反馈点、危险操作/主 CTA/状态标签的视觉优先级

---

## Step 9: 强制自检

输出前必须检查：
- 用户是否始终知道系统状态
- 是否存在无反馈等待
- 是否存在不可恢复错误
- 是否过度依赖弹窗
- 状态定义是否不全
- 键盘路径是否合理 / 焦点是否清楚
- AI 不确定性是否被伪装成确定性
- 同一交互在不同 persona 下是否可能失效
- 是否遗漏了数据前提（sync / init-state / backfill）
- 是否区分了"逻辑坏了"与"数据没准备好"
- 整体是否像成熟产品而不是 happy path demo

---

## 诊断模式（强化版）

进入条件：线上问题 / 改版痛点 / 流程断裂 / "我这里正常，别人那里有问题"

诊断模式优先做：
1. 反推场景与任务流
2. 问题定位（P0/P1/P2）
3. 缺口归类：任务流缺口 / 状态缺口 / 恢复缺口 / persona 差异缺口 / 数据前提缺口
4. 判断是：局部修补 / 状态补齐 / contract 补齐 / 数据前提补齐 / 整体重构
5. 输出修复优先级

## AI 交互类型识别

按类型设计：
- **建议型** — 提供参考，用户决定是否采纳
- **生成型** — 产出内容，需确认/编辑
- **执行型** — 直接执行操作，需前置确认
- **协作型** — 与用户共同完成任务
- **监控型** — 持续观察并报告异常
- **代理型** — 代表用户执行多步操作

每种 AI 交互都要回答：
- 结果是否会自动生效
- 用户是否可以部分采纳
- 是否需要人工确认
- 是否需要审计线索
- 若失败或不可信，下一步怎么做
